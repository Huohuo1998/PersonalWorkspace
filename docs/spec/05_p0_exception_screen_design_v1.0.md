# Personal Workspace｜P0 关键异常与边界页面设计 V1.0

> 日期：2026-10-12  
> 状态：**高保真前的屏幕状态与交互规格草案**（供视觉评审和未来实现验收）  
> 依据：已确认的 PRD、全站 UX V1.1、视觉基线 V2.0、`02_critical_flows_and_edge_cases_v1.0.md`、`03_acceptance_matrix_v1.0.md`。  
> **只做设计；没有系统开发、API 实现、资金操作或测试执行。**

## 0. 本轮边界与共通约定

- 对象实际发生与计划严格分开：日程 Task、饮食菜单、采购清单不会自动生成 Financial Transaction / Workout Session / Meal Record。
- 操作确认的视觉结果只能来自可信持久化响应。演示原型中的“成功”只是样例，不代表真实保存。
- 跨模块进入目标页携带稳定来源 ID 与用户当前视图上下文；成功/取消回到来源，来源无效时退回安全入口。
- 高风险操作不能因为网络超时就立即允许产生第二次相同事实；若结果未知，先查询/核对原提交状态，避免盲目重试。
- 下文的 `SCREEN-*` 为**设计屏幕标识**，不是路由、接口、数据表字段或开发任务。
- 桌面高风险核对宜使用独立抽屉/弹层且保留来源；手机高风险核对宜使用独立全屏步骤；训练手机底部操作固定并留安全区；采购单手勾选区域不小于建议的 44×44px。

## 1. 资金高风险操作｜页面状态设计

### 1.1 共通流程

`SCREEN-FIN-01 编辑` → `SCREEN-FIN-02 核对` → `SCREEN-FIN-03 提交中` → `SCREEN-FIN-04 成功`；失败分为：

- `SCREEN-FIN-05 校验/业务拒绝`：具体指出不合法字段、账户失效、超额度等，返回可编辑页，保留输入。
- `SCREEN-FIN-06 结果未知`：请求超时或连接中断且不知交易是否已执行。界面显示“正在核对本次提交状态”；禁止诱导用户立刻重新创建第二笔。核对确定失败才可重试；成功则展示同一笔交易；无法确认时明示状态未定并提供查询/人工核对入口。
- `SCREEN-FIN-07 数据发生变化`：核对页开启后账户余额或可退额度变化，标记原摘要已过期，强制重新获取余额、计算影响并再次核对。

**SCREEN-FIN-02 必含项目**：操作类别、发生日期、金额和单位、转出/到账或关联原交易、交易后影响摘要；信用还款明示“非新增支出”，转账明示“非收入/支出”，余额校正展示原余额/核实余额/差额及原因，退款展示实际退款月份、原交易及当前累计可退额。

### 1.2 四种高风险业务

| 操作 | 屏幕内容 | 关键校验与拒绝提示 | 完成后的显示 |
|---|---|---|---|
| 自有账户转账 | 转出/转入账户、金额、实际日期、两侧预计余额 | 两个账户不可相同；金额有效；是否允许余额不足按未来已确认策略校验 | 一条有唯一标识的关联转账，双方资产一增一减，非收支 |
| 信用卡还款 | 付款账户、信用账户、金额、日期、资产减少/债务减少 | 信用账户必须为负债账户；溢缴款等未确认规则不能擅自假定 | 信用卡欠款减少，不再增加消费 |
| 原交易退款 | 来源支出、剩余可退金额、退款日期、真实回流账户、分类抵减 | 累计退款不能超过可退金额；来源权限/状态有效；跨月、非原账户退款需显式确认 | 原交易保留；退款期的对应分类净支出抵减；对应资产/债务真实变化 |
| 账户余额校正 | 系统当前余额、用户核实余额、计算差额、原因 | 空原因禁止；提交前发现新交易则需重新核对；负债显示欠款方向清晰 | 形成可审计的调整事实，不归类为日常收支 |

### 1.3 微文案示例

- 核对：“请确认 **¥350.00** 从工资卡转入旅行储蓄卡。此操作不计入月收入或支出。”
- 处理中：“正在确认本次操作结果，请勿重复提交。”
- 结果未知：“网络已中断，暂时无法确认资金操作是否完成。请先核对交易记录，不要再次发起相同转账。”
- 版本冲突：“核对期间账户数据已更新，请重新查看金额变化后确认。”
- 退款：“本次退款将抵减实际退款月份的相关分类净支出，原消费记录仍然保留。”

**备注**：示例金额是假设情境，不是用户的真实金融数据。

### 1.4 桌面/手机差异

- 桌面：列表/账户详情在左侧；核对操作用侧面板或居中对话框，确保资金来源和目标名称始终可见。
- 手机：编辑 → 核对 → 状态结果，采用明确步骤；取消返回后保留来源业务上下文；提交按钮占据安全触控区。
- 返回时不可丢失原交易 ID、原列表筛选、滚动位置；从饮食采购单进入时显示“来源：采购清单”。

## 2. 训练会话、自动保存与恢复｜页面状态设计

### 2.1 会话状态

正式业务会话：`IN_PROGRESS / PAUSED / COMPLETED / ABORTED`。`dirty / saving / saved / failed / conflict` 是**编辑保存状态**，不是新增训练会话状态。

- `SCREEN-FIT-01 活动训练`: 当前动作和组记录占主要空间；顶部训练名称、完成组数、保存反馈；底部固定暂停/结束操作。
- `SCREEN-FIT-02 保存失败`: 当前未确认输入保留；展示失败原因及重试；禁止展示“已保存”。
- `SCREEN-FIT-03 恢复入口`: 回到概览时显示未结束的训练名称、最近已确认保存时间、完成组数、继续训练/中止并保留实际入口。
- `SCREEN-FIT-04 活动会话冲突`: 尝试启动另一详细训练时，显示既有会话，只有继续/先结束原会话/取消，无覆盖原会话快捷方式。
- `SCREEN-FIT-05 多设备编辑冲突`: 发现旧版本修改时禁止无声覆盖。显示服务器已存版本与本端待提交修改的区别，提供重新加载已存版本或核对后重试；本端未保存修改需清晰提醒可能丢失。
- `SCREEN-FIT-06 结束核对`: 总组数、实际完成组数、未完成组数、动作及实际数值快照，确认“完成”或“中止”；待保存未完成时阻止最终提交。
- `SCREEN-FIT-07 结束结果`: 真实训练历史中的 COMPLETED/ABORTED；只有明确关联的日程实例按已确认规则更新。

### 2.2 关键转移及异常

| 入口/动作 | 正常流程 | 异常处理 |
|---|---|---|
| 修改重量/次数或勾选一组 | 本地 dirty → 保存中 → 服务端确认已保存 | 失败保留输入和重试，不能凭 UI 演示状态当成功 |
| 暂停后离开 | 持久化 PAUSED，保留会话 ID | 保存失败时不得谎称暂停已经同步；提示当前状态待确认 |
| 再次打开运动页 | 检测已有活动会话，优先展示恢复入口 | 不能顺手创建第二条会话 |
| 同一账号两台设备打开会话 | 服务端会话唯一性；展示当前数据版本 | 发生编辑冲突时明示，禁止最后写入者悄悄覆盖 |
| 结束/中止 | 核对实际完成组 → 保证保存完成 → 确认最终状态 | 保存中、失败或冲突不能继续虚假完成；不补齐计划未做组 |
| 结束请求网络超时 | 核实同一会话的最终状态 | 不创建新会话以代替旧会话，避免重复结算 |

### 2.3 手机专注模式

- 当前动作、重量/次数（或时间）字段和完成组勾选最醒目。
- 数字键盘出现时训练主数据仍可阅读、上下滚动；固定底部操作区不遮挡当前编辑字段。
- 保存状态常驻但低干扰；失败升级为较明显提示，可重试；不停弹成功消息。
- 活动会话处于 PAUSED 时禁止意外编辑；恢复后才允许修改。
- 快速散步/跑步等完成记录不是持久活动会话，不受“仅一条详细活动会话”限制。

### 2.4 微文案示例

- “已保存至 09:42。您可以继续训练。”（时间必须来自真实确认）
- “这一组还未保存成功。数据暂时保留在当前页面，请重试。”
- “发现一条进行中的训练：全身力量 A。继续原训练，或先结束并保留已有记录。”
- “计划 9 组，实际完成 5 组。未完成的 4 组不会计入实际训练。”

## 3. 菜单修改与采购差异｜页面状态设计

### 3.1 四类数据清楚区分

1. 菜单：未来计划条目及食谱份数。
2. 理论食材需求：从可信结构化食谱和兼容单位换算出的结果，可能不完整。
3. 采购快照：用户生成后可人工编辑、勾选已购买的清单。
4. 实际经济交易：真实付款后，才在经济模块创建并关联。

`SCREEN-DIET-01 采购列表` 展示名称、数量、单位、勾选、来源与“人工修改”标识；`SCREEN-DIET-02 差异摘要` 展示旧需求与新需求；`SCREEN-DIET-03 差异明细` 按新增、增加、减少、无法换算、人工保护/已购保护分组；`SCREEN-DIET-04 应用确认` 明确只修改哪些行；`SCREEN-DIET-05 补购建议` 将已购买的数量与新增总需求核对后提出新的**待采购**行；`SCREEN-DIET-06 关联付款` 跳到经济模块表单，由用户实际填写付款金额/账户并保存。

### 3.2 关键算例（同单位、确定需求）

**鸡蛋，单位“个”**：原生成需求 2 个，已有“已购 2 个”的确认记录；更新后的菜单需要 4 个。

| 指标 | 显示 |
|---|---|
| 原需求 | 2 个 |
| 当前已购 | 2 个（受保护） |
| 新理论需求 | 4 个 |
| 建议待补购 | 2 个 |

**用户确认后**：保留原“已购 2 个”的采购事实；新增“待购 2 个”的补购建议/行。不得把已购 2 个的原数量改成 4 个，亦不得静默自动勾选新增行。

**需求减少**：如果当前已购 4 个、新理论需求 2 个，保留已购 4 个的事实；只在差异提示中说明超出新计划需求 2 个，不生成负数采购项，也不删除购买历史。

**用户手改**：用户已将鸡蛋数量改成 3 个，即便理论需求为 4 个，也要保留人工数量并显示“建议补购 1 个（需确认）”，不能直接覆盖为 4。

**单位不兼容**：2 个番茄与 200g 番茄，如不存在已验证的换算关系，保持两行且提示人工核对，不能凭名称自动相加。

**自由菜单**：若只写“午餐吃个家常菜”，缺失结构化食材，不推断精确购物量；提供人工补充入口。

### 3.3 防重复与快照版本

- 每张采购清单能追踪其所依据的菜单版本或等价快照标识（概念约束，并非数据库字段设计）。
- 用户取消差异核对后，原采购快照、已购勾选和人工数值原样保留。
- 重复应用同一份确认的差异，不应产生重复的补购行；后续再次改菜单时只处理新的差异。
- 来源食谱历史改变，不应悄然改写已生成且用户已编辑的采购事实。

### 3.4 从采购到财务

`采购清单 → 记录实际支出 → 财务记账/账户确认 → 保存 → 返回采购清单`。

- 采购清单、付款交易各有稳定身份；允许实际多次付款关联同一份清单，但不得虚构付款。
- 勾选所有采购项**不**等于已付款。
- 从财务取消、提交失败或来源失效时分别显示取消/失败/安全入口，不生成幽灵交易。

## 4. 全站异常、隐私与返回流程

### SCREEN-SYS-01 完整隐私遮蔽

开启后隐藏敏感金额、摘要比率、图表曲线/坐标/hover 提示、会反推金额的说明文字以及敏感测量数据（按用户已定隐私范围）；恢复显示须遵循同一持久化的用户偏好。遮蔽不等于数据访问权限；无权访问时必须拒绝读取。

### SCREEN-SYS-02 加载失败、真实零值与空状态

- 加载失败：“暂时无法获取数据，请重试”，不能展示“¥0.00”。
- 真实零值：可信查询成功，返回 0 时才显示“¥0.00”。
- 空状态：没有账户/食谱/训练计划等，显示可执行的第一步，而非假数据。

### SCREEN-SYS-03 来源失效的跨模块返回

目标操作完成后来源对象若已删除、失效或权限变更，则提示“原来源已无法访问”，返回目标或来源领域的安全入口；不可自动推断新的来源对象或泄露他人内容。

### SCREEN-SYS-04 重复与未知提交

对于新交易、结束训练、生成关联真实用餐等创建/结算操作，重复点击与网络未知结果不应重复生成业务事实。页面提供“核对本次状态”的反馈，不以不确定态强行显示成功或失败。

## 5. 屏幕交付索引及响应式规格

| 设计屏幕族 | 关键 ID | 桌面呈现 | 手机呈现 | 对应既有验收 |
|---|---|---|---|---|
| 财务核对提交 | FIN-01～07 | 编辑抽屉 + 核对弹层/页 | 编辑页 → 核对页 → 结果页 | PW-F02～05、PW-F08、PW-F10、PW-G03～04 |
| 训练自动保存与恢复 | FIT-01～07 | 训练工作区 + 冲突提示 | 专注模式 + 固定底栏 + 恢复入口 | PW-T01～09、PW-G03～04 |
| 采购差异与补购 | DIET-01～06 | 清单/差异并排或抽屉 | 勾选清单 + 独立核对页 | PW-E01～04、PW-E07、PW-E11、PW-G05 |
| 隐私与系统异常 | SYS-01～04 | 页面内原位提示 | 页面内原位提示/独立错误页 | PW-G03～10、PW-G13～15 |

> 上表使用 `SCREEN-*` 名称；简写 FIN-01 等均指对应 `SCREEN-FIN-*`。

## 7. 开发前仍需产品/技术分别确认的事项

**产品规则待细化**：现金/银行账户透支策略；信用卡溢缴款处理；跨账户退款与对账展示；采购单位等价换算库范围；采购已购数量及人工数量与补购合并的具体交互；敏感测量数据的隐私遮蔽范围。

**技术方案未开始**：资金交易唯一性、状态查询与并发核验、训练保存版本冲突处理、采购快照版本与核对记录、鉴权和数据隔离的具体实现。

不得把本页概念字段、设计按钮或示例数值视作已经批准的数据库结构和接口设计。

## 8. 本轮评审结论

- 财务：核对步骤、未知提交结果、原事实关联与版本重核列为 P0 设计范围。
- 运动：服务端实际保存确认、恢复入口、单活动会话和多端编辑冲突列为 P0 设计范围。
- 饮食：采购独立快照、差异核对、已购/手改保护、补购项去重列为 P0 设计范围。
- 全站：来源上下文、安全返回、完整隐私遮蔽、空/零/错误区分列为 P0 横向范围。
- **文档说明的是后续需展示和验证的行为，不表示这些屏幕已有高保真最终签收，更不表示网站已开发。**
