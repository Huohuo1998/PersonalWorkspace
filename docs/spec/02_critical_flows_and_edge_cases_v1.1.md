# Personal Workspace｜关键业务流程与边界场景 V1.1

> 状态：开发前设计收口材料（流程规范）；2026-10-12。  
> 本文不包含实现代码、数据库脚本或技术选型。  
> 解释冲突时以已确认 PRD、UX V1.1 和全站视觉基线 V2.0 为准。

## 1. 通用端到端交互协议

### 1.1 统一导航上下文

来源界面携带：`source_domain`、`source_object_id`、可选执行实例 ID、目标操作类型、日期/筛选/滚动定位等 UI 上下文；目标操作回传成功/取消的明确结果并返回合法来源。这里是**概念字段**，不是已经冻结的接口定义。来源对象删除或权限失效时返回安全入口，并提示关联不可用。不能只凭标题或模糊日期进行关联。

### 1.2 统一保存状态机（UI 语义）

- `idle/dirty` → `saving` → `saved`：确认成功后才可以展示最终成功。
- `saving` → `failed`：保留输入，清晰展示哪些变更还未确认保存、重试入口和可能的冲突。
- 需要二次确认的最终提交：编辑 → 核对 → 提交中 → 成功/失败；失败不自动退出页面。
- 即时勾选可乐观更新，但确认失败必须回滚或重新同步并告知用户。
- 非幂等操作（交易、结束训练等）重复点击、断网重试时不能产生双份真实事实；提交中禁用重复操作不是唯一保障。

### 1.3 其他通用约束

- 空值（无数据）、零值（真正为 0）、加载失败（未知）具有不同展示。新用户不显示虚构余额/完成率。
- 日期/时间以用户上下文展示；保存与历史操作均保留正确事件实际发生时间，不把显示日期猜为实际发生日期。
- 隐私开关按用户保留偏好：主要金额、相关说明、图表、百分比、tooltip、辅助文案同步隐藏；访问控制与隐私遮蔽分别生效。
- 项目内的个人数据应仅对授权用户可见；页面路由和后端查询都应尊重隔离，不能通过换 ID 获取他人数据。
- 后续 AI 功能不得被当成当前 MVP 的必需输入或可用能力。

## 2. 日程域

### FLOW-SCH-01：一句话进入收集箱

**起点：** Dashboard 全局「+」或日程收集箱；用户只填写标题。  
**路径：** 快捷输入 → 保存 Task → 出现在收集箱 → 可再次编辑分类、项目、截止/执行安排。  
**预期：** Inbox 是位置属性，不是单独的执行状态；不强制设置日期或项目。重复提交仅一条 Task。

### FLOW-SCH-02：安排今天但没有截止日期

**起点：** 收集箱中的未安排任务。  
**路径：** 选择「安排今天」→ 增加“今日执行意图”或当前日的排期 → Dashboard/今日重点可见。  
**预期：** 无需将 Due 修改为今天，也不必填写具体时刻；执行时间和截止时间独立，今日重点可包含没有截止日期的任务。  
**异常：** 来源收集箱数据已删除时操作失败并保持列表一致。

### FLOW-SCH-03：任务与事件同时在日历

- 09:30–10:30 独立 Event 有时间块和事件标识，不显示任务完成勾选。
- 14:00 排期 Task 可在时间线上完成/延期；仅有 Due 的 Task 只显示期限提示，不伪造全天占用。
- 当日/当周显示领域来源 Task 时可进入来源专业模块；手动勾选只更新任务状态，不产生专业记录。

### FLOW-SCH-04：重复任务单次改期

**路径：** 打开重复任务当前实例 → 选择只调整本次 → 修改当前实例日期 → 后续实例保持模板原样。  
**约束：** 由运动/饮食等源领域创建的重复计划，长期计划变更必须转到专业领域；Schedule 不擅自改源计划。历史已完成实例保持不变。

### FLOW-SCH-05：逾期事项

昨日到期、未完成任务进入待关注，保留原 Due；用户可延期、取消或完成，系统不会自动把截止日期改为今天。完成历史可折叠，不参与当前待办提示。任务状态只使用正式状态，不因逾期创建额外执行状态。

## 3. 经济域

### FLOW-FIN-01：支出与信用卡购买

**普通账户支出：** 用户选择金额、日期、分类、账户 → 提交 → 一笔支出记录、对应资产余额减少。  
**信用卡购买：** 同样形成一笔支出，但信用卡负债增加；资产账户不当场减少。  
**约束：** 一笔消费只在实际消费日期计入一次支出；保存失败/重复请求不得多笔入账。

**负余额专项交互（POL-FIN-01）：** 当账户原有 50、真实支出 80，表单先显示预计余额 −30 与核对入口，明确确认后可留存这笔支出；不得通过虚构收入配平。

### FLOW-FIN-02：内部转账

**路径：** 选转出、转入账户、金额和实际日期 → 核对来源/目的地 → 确认 → 两侧余额同步变化。  
**预期：** 全部自有账户资产合计不因内部转账变化；月收入/支出不变；专用储蓄账户余额变化可以影响所绑储蓄目标进度。  
**异常：** 相同账户、非法金额、余额不足（如策略禁止透支）给出明确阻止理由；`POL-FIN-01` 已批准：允许如实补录导致负余额的真实交易，但必须展示预计负余额和二次核对。

### FLOW-FIN-03：信用卡还款

**路径：** 银行/其他真实资产账户 → 信用卡负债 → 核对 → 提交。  
**预期：** 资产减少、负债减少，净资产理论上不因还款发生额改变；不生成第二笔消费。  
**异常：** 超过负债、错误卡片、重复提交均需妥善处理；`POL-FIN-02` 已批准：若真实还款超过欠款，清楚提示并将多余部分记为溢缴款，欠款归零，净资产只计一次。

**信用卡溢缴专项交互（POL-FIN-02）：** 欠款 500、银行还款 600，显示预计欠款 0 与溢缴 100，并确认银行资产 -600；还款不纳入新支出，卡内溢缴在净资产仅算一次。

### FLOW-FIN-04：关联退款

**路径：** 原始支出详情 → 发起全部/部分退款 → 输入实际退款日期与金额、退款回流账户（默认原账户但允许按实际情况核对） → 提交。  
**预期：** 退款带有原始支出 ID；本退款月份的对应分类净支出抵减；若回原信用卡则相应负债减少；累计退款原则上不超过被退消费的可退金额。  
**异常：** 原交易不可用、退款超额、已存在多笔部分退款、跨月退款、退款走另一真实账户，都需校验与明示。不可直接覆写原消费使历史消失。

**已确认的跨账户退款专项路径（POL-FIN-03）：** 原信用卡消费 320 → 实际现金退款 100 → 原卡状态不因这笔现金退款改变；现金账户 +100；退款所属月份原消费分类净支出 -100；界面标明到账账户不同且保留原消费关联。

### FLOW-FIN-05：余额校正与历史

**路径：** 账户详情 → 输入核对后的实际余额 → 显示原余额、差额、影响和原因 → 二次确认 → 记入可追溯的校正记录。  
**预期：** 校正影响账户当前余额，但不作为普通收入/消费统计；财务历史必须可追溯。  
**异常：** 同期发生其他交易时应重新核对余额；校正确认界面不可用过期显示覆盖新交易。

### FLOW-FIN-06：预算与储蓄

- 月度总预算与分类预算共用当期消费真实数据；总额与分类限额不二次相加。
- 预算可用额度 ≠ 任意实际账户余额；未设置预算显示“未设置”，不是“0 元剩余”。
- 储蓄目标与一个真实专用账户绑定；一个账户最多一个有效目标；设定目标金额不创建资金；专用账户存款通过真实转账/入账影响进度。

## 4. 运动域

### FLOW-FIT-01：开始详细训练

**路径：** 概览今日计划或训练页面 → 查询当前用户活动会话 → 无活动会话才允许新建 → 记录开始时间并进入专注模式。  
**异常：** 若已有 IN_PROGRESS/PAUSED 的详细会话，展示“继续原训练 / 结束原训练并保留实际 / 取消”；不同设备并发同样遵守唯一会话原则。

### FLOW-FIT-02：逐组记录与自动保存

**路径：** 编辑组重量/次数/时长或勾选组完成 → 标记 dirty/saving → 服务器成功响应 → saved。  
**失败：** 保留当前输入，显示 failed 与重试；页面关闭后**至少恢复上次已确认保存的内容**，MVP 不承诺完全离线持久化。多设备同时修改时需避免无声覆盖；未提交成功不能声称已保存。

### FLOW-FIT-03：暂停、恢复、完成与中止

- 暂停保留已确认组及活动会话身份，不等于已完成训练；再次登录优先提示恢复。
- 结束训练先核对真实完成组及未完成组；确保待保存修改同步成功，再提交最终状态。
- `COMPLETED`：形成完整会话结局，但不会补齐未做的训练组；明确关联的日程实例可闭环。
- `ABORTED`：保留已经发生的训练内容、标记中止，不把未做组计为完成。
- 用户可以当天完成多个先后独立的会话；自由散步等快速记录不占持续会话。

### FLOW-FIT-04：模板更新与历史

历史训练详情应呈现记录时的动作/实际参数快照。计划模板变化不会回写历史。用户更正历史需保留必要审计、修改者和时间；身体/恢复主观记录独立可选，不阻塞训练结束。

## 5. 饮食域

### FLOW-DIET-01：已有食谱到周菜单

**路径：** 已有食谱库检索/筛选 → 核对食材、制作时间和已知禁忌 → 选某天某餐和份数 → 保存菜单。  
**预期：** 菜单只是计划，不自动创建 Meal Record；自由文本菜名可作为菜单但不能据此生成精确食材清单。  
**安全：** 过敏原筛选依赖完整已知数据，未知配料必须明显提示核实，不得承诺绝对无过敏原。

### FLOW-DIET-02：采购生成与单位聚合

**路径：** 用户选择菜单范围 → 计算有结构化食材的菜谱用量 × 份数 → 仅在相同或已校验可转换单位下合并 → 生成独立采购清单。  
**预期：** 2 个番茄与 200g 番茄不因名称相同盲目合并；不同食材 ID 同名但规格不同需提示核对；缺食材数据的菜谱进入“待人工补充”，不伪造数值。  
**边界：** 无全量库存抵扣，这是后续非 MVP 功能。

**已确认单位白名单（POL-DIET-01）：** 自动换算限 g/kg、ml/L 和同物品同规格的件数等可靠确定转换；不同量纲不合并，未知规格提示人工核对。

### FLOW-DIET-03：菜单更新与差异核对

**前提：** 原采购清单已生成，部分食材人工调整或标记已购。  
**路径：** 菜单改变 → 计算最新理论需求与现有采购清单的差异 → 展示增加/减少/缺失/无法换算 → 用户决定是否应用安全差异。  
**规则：** 未购买且未人工修改的自动生成行，在用户确认后可更新；已购/人工调整行不得静默覆盖；需求增加时显示待补购数量（例如已购鸡蛋 2 个、最新需求 4 个，可建议新增待购 2 个）；需求减少不得删除已购事实，或将剩余需求算成负数。  
**冲突及多轮增量（POL-DIET-02）：** 用户同意后仅调整可安全编辑的未购、未手改行；已购与手改历史保留。同一菜单版本/差异重复确认不得双重补购。例：已购2、未购2、新需求5→只补差额1或将未购2调整为3；不再创建待购3。

### FLOW-DIET-04：真实采购支出

**路径：** 采购清单中选择「记录付款」→ 跳转经济表单并预填关联上下文 → 用户选择真实账户、日期及实际支付金额 → 提交 → 返回采购清单并显示关联。  
**预期：** 采购勾选不直接生成真实付款；一份清单允许按实际需要关联多次交易，但绝不能假定清单金额等于实际支出。

### FLOW-DIET-05：菜单预填真实用餐

**路径：** 今日菜单中的某餐选择「记录实际」→ 表单预填计划菜名/份数 → 用户核对或改写实际内容及可选用餐来源 → 明确保存 → 新增 Meal Record。  
**预期：** 取消不产生真实记录；原菜单保持不变；真实自炊次数只统计用户实际标记自炊的记录。快速输入可完全绕过菜单和食谱。

### FLOW-PRIV-01：全局隐私遮蔽与必要输入（POL-PRIV-01）

**浏览场景：** 打开全站隐私 → Dashboard 和 Finance 的金额、预算百分比、图表坐标/tooltip/通知同步遮蔽；Fitness 身体测量、恢复状态、训练表现摘要同步遮蔽。切换账号时按各自偏好读取。

**主动操作场景：** 用户在隐私开启情况下主动进入记账、训练逐组编辑或身体测量表单 → 当前任务需要的数值输入可见并可改，其他被动摘要继续遮蔽；退出编辑仍遵循原全局隐私偏好。**不能**利用隐私操作绕过鉴权。

## 6. 视觉、权限及失败场景矩阵

| 典型场景 | 应展示什么 | 禁止行为 |
|---|---|---|
| 全新用户打开 Dashboard | 引导先新增任务/账户/运动/用餐；可跳过 | 使用虚构零余额、完成率 |
| 财务 API 查询失败 | 加载失败、重试，不显示过期数据为“最新” | 把错误当作 0 元 |
| 隐私模式开启 | 数值/百分比/敏感图表/tooltip/说明同步遮蔽 | 只隐藏主卡片金额 |
| 高风险财务提交中 | 保持核对态、不可重复生成 | 连点产生重复交易 |
| 财务账户被停用 | 明示不可选择及原因 | 提交到未知账户 |
| 日程来源已失效 | 返回合理入口，并提示链接失效 | 访问他人对象或空白页 |
| 领域计划被取消 | 可保留已经完成的真实历史 | 级联删除经济/运动/饮食记录 |
| 训练自动保存失败 | 明确失败，保留输入与重试 | 显示“已保存”或丢弃输入 |
| 训练跨设备并发 | 引导恢复/冲突解决 | 同时创建两条活动详细训练 |
| 食谱过敏原未知 | 标明信息不足、人工核查 | 保证“完全安全” |
| 菜单变更且食材已购 | 展示补购/减少差异，保护已购事实 | 全量重生覆盖清单 |
| 采购勾选全部完成 | 仅反映购物状态 | 自动生成支付交易 |
| 用户已完成日程训练任务 | 任务已完成，但专业训练为空仍为空 | 自动创建完成的训练会话 |
| 筛选无结果 | “没有符合筛选条件的记录” | 误示“整个账号从未有记录” |
| 用户切换设备/刷新页面 | 优先恢复已持久化状态和筛选上下文 | 以不可信本地状态覆盖服务端事实 |

## 7. 待后续设计细化、但不阻碍当前原则冻结的事项

1. 时间展示、跨时区数据与重复实例的具体日期选择交互；需在可测试原型中核对。
2. 财务负余额/信用卡溢缴款/跨账户退款的**产品规则已批准**；其完整桌面和手机核对状态稿仍需要设计验证，技术实现另行评审。
3. 采购不足量的拆分、手工添加/删除/合并及单位口径的完整差异交互。
4. 运动保存失败后的本地草稿提示、多设备冲突 UI、固定底部栏与软键盘兼容。
5. 登录/首次欢迎、无权限、404、全站加载失败等完整高保真状态稿。

这些是**需要在未来开发前补齐或验证的事项**，不是已实现功能或用户尚未确认的九项视觉决策。
