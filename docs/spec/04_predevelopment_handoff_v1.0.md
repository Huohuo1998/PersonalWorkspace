## 3. 范围界限

### MVP 包含

- 账号身份及每用户的数据隔离、个人偏好。
- Dashboard：今日定时安排、今日重点、快捷操作、四领域摘要、待关注、隐私遮蔽。
- 日程：收集箱、任务、独立事件、日期视图、轻项目、重复任务实例与历史、领域关联。
- 经济：资产账户/信用负债、收支/转账/还款/退款/校正、预算与储蓄目标、可追溯历史。
- 运动：目标与计划、动作/模板、详细训练逐组记录、自由运动、真实历史、身体/恢复可选记录。
- 饮食：预置与个人食谱、菜单、采购清单及差异、实际用餐记录、简单自炊习惯统计。

### MVP 不包含

AI 专业教练与内容自动生成、银行流水自动同步、穿戴设备同步、完整食材库存、强制卡路里和宏量营养核算、多人共享预算/训练、拖拽自由配置首页、通用企业级工作流引擎。

## 4. 领域对象与事实所有权（概念模型）

| 对象 | 所属领域 | 规则重点 |
|---|---|---|
| User / Preference | 账号和设置 | 隔离所有私有数据；保存隐私显示偏好 |
| Task / TaskOccurrence | Schedule | 行动状态、Due 与 Scheduled 分离；单次重复实例独立 |
| Event | Schedule | 日历独立事件，不使用任务完成语义 |
| Project | Schedule | 轻量任务分组，不替代领域计划 |
| Account / CreditLiability | Finance | 资产与负债分别计量 |
| Transaction / Refund / Adjustment | Finance | 真实金额、发生日、关联来源、审计，不得重复计账 |
| Budget / SavingsGoal | Finance | 预算为计划，储蓄绑定真实专用账户 |
| FitnessGoal / TrainingPlan | Fitness | 领域计划来源，可与日程实例关联 |
| Exercise / WorkoutTemplate | Fitness | 模板可演化，但不得覆写历史训练 |
| WorkoutSession / WorkoutSet | Fitness | 逐组真实事实、状态机、自动保存与唯一活动会话 |
| BodyMeasurement / RecoveryRecord | Fitness | 可选、独立于训练完成 |
| Recipe / Ingredient | Diet | 数量/单位、份数、食谱快照与已知禁忌 |
| MealPlan / PlannedMeal | Diet | 未来餐食计划，不等于已消费 |
| ShoppingList / ShoppingItem | Diet | 独立采购快照，受保护的手工/已购状态 |
| MealRecord | Diet | 实际用餐事实，可选来源、自炊统计基于真实记录 |
| BusinessLink | 相关域之间的关联机制 | 概念性交叉引用，不能以标题/时间猜测唯一对应关系 |

**总原则：** 日程管“做什么、何时做”，专业模块管“实际发生了什么”。勾选 Task 不自动伪造 Transaction/WorkoutSession/MealRecord。真实领域事实可根据稳定关联驱动日程实例闭环，但不能擅自修改来源长期计划。

对象名是产品概念，不是最终数据库表、类或 API 名称；未来须由独立技术设计确认。

## 5. 关键状态与生命周期

### Schedule

Task：TODO、IN_PROGRESS、COMPLETED、CANCELLED；Inbox、Overdue、Today、Postponed 是组织/计算维度，不应另造同等 Task 状态。Event 与 Task 独立。

### Finance

交易的新增、更正、退款/冲正及审计独立；信用卡消费计一次支出，信用还款不是再次支出；同账户/用户内转账不是收入或支出。所有变动以实际日期与真实对象关联为依据。

### Fitness

详细 WorkoutSession：IN_PROGRESS / PAUSED / COMPLETED / ABORTED；同用户最多一条活动会话（IN_PROGRESS+PAUSED），跨设备生效。自动保存组内容与“完成/中止”的最终确认分离。

### Diet

MealPlan 与 MealRecord 独立；ShoppingList 生成后独立存在，其购物状态和用户调整受保护；菜单变化只产生需求差异建议，不静默覆盖采购事实。

| 页面或界面族 | 核心屏幕 | 关键特殊状态 |

| 运动身体 | 测量、主观恢复 | 无数据、可选独立反馈 |
| 饮食概览 | 今日菜单/记录/采购摘要 | 无计划、已计划未实吃 |

## 7. 设计交付物完成定义（Definition of Ready for Development）

未来用户明确同意进入开发前，建议满足以下门槛：

1. **决策一致**：所有已冻结决策有唯一编号，PRD、UX 与视觉互不冲突；变更有决议记录。
2. **视觉完整**：全站导航、组件 Token、桌面/手机主要屏幕、关键异常场景以及设计尺寸规范可用。
3. **用户旅程闭环**：任务→领域执行、采购→记账、菜单→真实用餐、训练恢复→结束等流程可从入口走到成功或失败结束态。
4. **状态与数据边界明确**：所有涉及真实资金、实际训练和实际用餐的操作有独立事实语义；幂等与历史更正要求可核查。
5. **权限与隐私明确**：用户隔离、遮蔽范围、无权限/失效链接具备设计与验收标准。
6. **性能/可靠性目标有定义**：具体指标由后续技术方案提出并与产品共同确认，不在此凭空承诺。
7. **验收可测试**：P0 条款能写出测试步骤、预期数据变化与拒绝条件。
8. **技术设计另立阶段**：选型、部署、存储、认证、并发、日志、可观察性、回滚等不由当前视觉文件代替。
9. **用户明确批准启动**：在此之前不得将设计任务自动变成开发实施。

## 8. 当前待设计收口事项（按优先级）

### P0：继续完善，不能因视觉冻结而忽略

- Dashboard 隐私模式的**所有**衍生金额、百分比、图表和辅助提示。
- 日程“安排今天”而无 Due 的页面表现，以及 Task/Event 单次实例规则。
- 财务高风险交易核对、重复提交、失败重试、实际日期和历史更正的完整状态。
- 运动单活动会话、自动保存失败、重新登录恢复、多设备冲突、软键盘下固定按钮。
- 采购差异中的已购保护、人工数量保护、正向补购、负向需求和不可转换单位。
- 跨模块返回、失效来源和取消不产生日志外假事实。
- 多用户数据隔离、未授权访问、全站加载失败与空状态的交互与验收设计。

### P1：视觉质量与效率

- 无障碍颜色对比与焦点态、200% 字体放大、多设备宽度适配。
- 列表筛选、排序、日期跳转、长文本截断、数值对齐、输入法表现。
- 初次使用引导、长期无数据及部分数据缺失的文案一致性。
- 表单字段校验与错误态文案、减少模糊确认弹窗。

## 9. 后续技术设计需要回答的问题（明确仍未决定）

这里记录**问题**而不是擅自给出实现决策：

- 身份验证与数据权限模型如何落地？
- 何种数据库及审计方式能保证真实财务账目一致、原交易与退款关联可靠？
- 训练单会话的并发约束、多设备写入冲突与自动保存协议如何实现？
- 跨领域数据联动如何做到稳定关联、幂等、故障恢复与最终一致？
- 采购清单快照与需求差异如何建模，如何表达补购和人工覆盖？
- Web 页面响应式、缓存/离线策略、日志监控、备份恢复及数据导出如何规划？
- 是否需要区分开发、测试、正式环境以及迁移升级方案？

**这些都是待未来开发立项后回答的技术问题；不得将本交接包理解为已经选择技术架构。**
