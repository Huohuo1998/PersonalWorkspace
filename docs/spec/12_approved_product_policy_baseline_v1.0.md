## B. 财务 PRD 补充（Finance）

### POL-FIN-01｜非信用资产账户负余额（已确认 B）

**业务事实：** 银行、现金、电子钱包等资产账户允许忠实记录已发生的负余额。支出或转账将使账户账面余额低于 0 时，核对界面必须显示预计账户余额、差额、关联账户及交易日期，以显著但不恐吓的警示提示用户二次确认。用户可确认已发生事实；不得生成虚构收入、自动贷款或强制修改金额“配平”。

**例：** 期初 ¥50、真实支出 ¥80 → 账户余额 **−¥30**，保留支出 ¥80。负数应被标识为“需核对账目”，预算剩余额度仍独立计算。

**交互：** 普通无异常支出仍为轻量录入；预计负余额才进入附加核对步骤。账户列表、详情及历史均可以准确展示负数。对真实转账允许负值，但显示转出余额影响；不得因界面验证逻辑阻止用户补录已发生的真实事实。

### POL-FIN-02｜信用卡溢缴款（已确认 B）

**业务事实：** 信用卡可因实际还款超过欠款而形成溢缴款；欠款与溢缴余额在界面**分别展示，不同时当作两份资产或负债**。超额还款需核对提示，但如已真实发生，应允许记录；还款不计收入或消费。

**一致的概念计算口径：** 用有符号卡余额 `C` 表示卡方欠款（正）或溢缴余额（负）：

- 信用卡消费 `C += 消费金额`，消费分类仅计一次支出。
- 还款 `C -= 还款金额`，实际付款的资产账户余额等额减少；不新增支出。
- 真正退回信用卡的退款 `C -= 到卡退款金额`，本期相应分类净支出等额抵减。
- **待还欠款** = `max(C, 0)`；**溢缴余额** = `max(-C, 0)`。
- **净资产参考值** = 其他资产账户合计 + 卡内溢缴余额 − 待还欠款；卡内溢缴余额不再被加入一次其他资产合计。

**例：** 欠款 ¥500，还款 ¥600 → 待还欠款 ¥0、卡内溢缴 ¥100；支付资产账户减少 ¥600；净资产因还款本身不变化。后续卡消费会抵扣溢缴余额，但依旧按消费发生额记录一次支出。溢缴资金退回自有银行账户按内部资金移动处理，不作为收入。

### POL-FIN-03｜退款到其他真实账户（已确认 B）

**业务事实：** 退款必须关联原始消费，保留原交易，按实际到账日期归属退款月份并冲减原消费所属分类的净支出。到账账户**默认原支付账户**，允许明确选取真实到账的其他资产或信用账户；只调整实际到账账户，不额外调整原账户。

**例：** 用信用卡消费 ¥320，实际退款 ¥100 进入现金账户 → 现金资产 **+¥100**；原卡欠款在本次现金退款中**不改变**；退款月份原分类净支出 **−¥100**。若退款真正回卡，才改变信用卡欠款/溢缴余额。

**交互：** 核对页显式显示原支付账户与实际到账账户是否不同、到账日期、预计资产/负债影响、剩余可退额度。累计退款不得超过被退原消费允许的金额。提交未知结果先查询原操作，禁止盲目重复创建退款。

### 财务事实检验矩阵

| 情况 | 资产效果 | 信用卡效果 | 当月收入/支出 |
|---|---|---|---|
| 资产账户支出 80，原有 50 | 相应资产 -80，允许 -30 | 无 | 支出 +80 |
| 欠款 500，从银行还款 600 | 银行 -600 | 欠款归 0，溢缴 +100 | 收入/支出均不变 |
| 信用卡消费 320 后现金退款 100 | 现金 +100 | 原卡不变 | 退款月净支出 -100 |
| 信用卡消费 320 后同卡退款 100 | 其他资产不变 | 原卡账面义务 -100 | 退款月净支出 -100 |

## C. 饮食 PRD 补充（Diet）

### POL-DIET-01｜可靠食材单位换算（已确认 B）

自动合并仅在**食材标识匹配、规格明确、量纲兼容、转换比率可靠**时生效：`1 kg = 1000 g`；`1 L = 1000 ml`；同种同规格且数量单位一致的件数可合并。重量/体积/件数**跨量纲不自动换算**，例如 `2 个番茄` 与 `200 g 番茄` 不合并，`1 袋` 未提供净含量不可猜算。模糊食材、缺少结构化配料、`适量` 等进入人工核对；人工确认仅针对已指明的清单差异，不自动确立全局食材知识换算常数。MVP 不引入全厨房库存或自动估算密度。

### POL-DIET-02｜采购快照与多轮增量补购（已确认 B）

清楚区分**当前理论需求 N**、**已购买数量 P**、**尚未购买的清单数量 U**、**人工调整/冻结的条目**，只在同食材同可换算单位下进行核算。

- 生成的采购清单是独立快照；修改菜单只产生**待核对的差异**，不直接改写已购或人工修改数量。
- 用户确认差异之后，允许调整未购买且未人工改动的自动生成条目；已购行永远保留采购事实，人工改动行保留值并要求用户显式选择处理。
- 未购计划存在时，建议**补购量**不得忽略既有未购条目：通常参考 `max(0, N − P − U)`，但人工改量、不同规格、部分菜谱缺失时只作提示且需用户核对。
- 若 `P + U > N`，展示“新计划需求减少／已有安排偏多”，不产生负数补购、不静默清除已购；未经确认也不裁剪人工未购条目。
- **重复应用**：同一菜单版本与同一轮已确认采购差异再次提交，不重复创建补购；之后菜单版本变动应基于当前已购/未购状态重新核对，而不是从旧差异重复累加。

**典型序列：** 已购 2 个鸡蛋，新需求 4 个 → 确认后补购 2 个；这 2 个仍未购买时菜单再增至 5 个 → 仅补充差额 1 个或把未改动的补购行调整为 3 个，不再重复生成 3 个；已购买数量超过新需求时提示超出计划而不删历史。

**额外边界：** 清单勾选不生成财务交易；用餐计划不生成 MealRecord；购买数量与食材库存不是同一个概念。

## D. 全站及运动/身体交互隐私补充

### POL-PRIV-01｜敏感摘要一键遮蔽，必要输入不受阻（已确认 B）

- **默认显示**仍沿用 Dashboard/全站已确认决策；用户开启全站隐私模式后，按用户持久化偏好覆盖：资产/负债/交易/预算、金额或比例、资金趋势、可反推数值的图表刻度与 Tooltip、通知和辅助文案，以及**体重、腰围、身体趋势、恢复状态和训练表现摘要**等敏感呈现。
- 只遮蔽文本主体而不遮蔽副标题、图表刻度、悬浮信息、趋势涨跌与衍生值，属于不符合要求的设计。
- 用户主动进入记账编辑、逐组训练、身体测量表单时，**当前操作必要的字段继续可读可编辑**；可提示“当前输入内容可能对旁观者可见”。被动浏览摘要、历史和非编辑详情应服从隐私遮蔽规则。
- 全局隐私偏好不因某次编辑而自动关闭。未来若设计“临时查看单条详情”操作，须额外明确其范围和自动复原条件，不能擅自默认全局解锁。
- 隐私遮蔽仅为**展示层**；任何情况下不可绕过用户鉴权、资源权限及跨用户数据隔离。
